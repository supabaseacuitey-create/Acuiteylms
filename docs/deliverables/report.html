Acuitey Solutions LMS — Initial System Design Section 01: Executive Architecture Overview

1. Executive Architecture Overview

The Acuitey Solutions Learning Management System (LMS) is architected upon Moodle LMS 5.2.3+ (Branch 502), providing an open, secure, and horizontally scalable digital learning ecosystem. The platform uniquely pairs Moodle's enterprise course management and assessment engine with Acuitey's proprietary Automated Dynamic Faculty Routing System.

Moodle Core Untouched

Zero core modifications. The entire upstream Moodle 5.2 code remains 100% standard and directly upgradeable with zero merge friction.

Dynamic Faculty Allocation

Intelligent Ola/Uber-style algorithm dynamically evaluates specialization, real-time availability, and active workload to match students with instructors.

Proposed Cloud Topology

Proposed Cloudflare Edge perimeter, Hostinger KVM (recommended Ubuntu LTS), Nginx, PHP-FPM OPcache, Redis (configuration to be finalized), and managed PostgreSQL.

Acuitey Solutions LMS — Initial System Design Section 02: Architecture Principles

2. Architecture Principles & Governance

To guarantee continuous maintainability, data integrity, and compliance across multi-year institutional lifecycles, four architectural pillars govern all engineering decisions:

01

Moodle Core Remains 100% Untouched and Directly Upgradeable

Under no circumstances are Moodle core application files in /lib, /course, /user, /enrol, or /admin altered. Moodle security patches and upstream point releases are consumed directly from official git tags without bespoke regression testing of overridden core routines.

02

Strict Encapsulation Within Standard Extension Subsystems

All custom Acuitey business logic is housed within supported Moodle extension hooks: the primary orchestrator resides in local/acuitey (local_acuitey), payment gateways in payment/gateway/, and UX customizations within theme/acuitey. Custom tables utilize Moodle's XMLDB database abstraction (mdl_local_acuitey_*).

03

Avoidance of Unnecessary Third-Party Plugins

Third-party community plugins introduce severe supply chain risks, database bloat, and upgrade incompatibilities. Acuitey mandates native Moodle capability utilization or direct custom development in local_acuitey, eliminating brittle external dependencies.

04

Asynchronous, Event-Driven & Stateless Scalability

Compute-heavy tasks—including multi-criteria faculty ranking, email dispatching, report compilation, and routing retries—are handled asynchronously through Moodle’s unified Event-Observer architecture (db/events.php) and ad-hoc task workers (\core\task\adhoc_task), preventing HTTP-FPM request timeouts.

"Custom Acuitey functionality resides exclusively in controlled extensions. Moodle core files remain pristine, preserving long-term upgradeability and total system stability."

Acuitey Solutions LMS — Initial System Design Section 04: Faculty Routing Engine

4. Automated Student-to-Faculty Routing Engine

The most critical custom capability in Acuitey LMS is the Automated "Ola/Uber-Style" Student-to-Faculty Dynamic Routing Engine. Rather than relying on static teacher course assignments, the system balances real-time pedagogical demand with instructor availability and workload capacity.

Dual Pipeline Execution: The routing engine operates an immediate synchronous evaluation pipeline for real-time requests, backed by a persistent Pending Queue & Scheduled Retry Engine for surge capacity management and administrative SLA escalation.

Acuitey Solutions LMS — Initial System Design Section 04: Faculty Routing Logic & Fallback

4.1 Multi-Criteria Evaluation & Fallback Workflow

The matching engine implements multi-stage filtering, dynamic mathematical scoring, and resilient exception handling to guarantee consistent service levels.

Multi-Stage Filtering Criteria

  • Subject Specialization: Matches requested course taxonomy against faculty competency tags stored in mdl_local_acuitey_faculty_prof.
  • Moodle Capability Validation: Confirms the instructor holds moodle/course:update and local/acuitey:mentor in the course context.
  • Real-Time Shift & Status: Evaluates active shift schedules and real-time online status stored in Redis cache.
  • Workload Cap Enforcement: Rejects faculty whose current_workload ≥ max_workload to eliminate instructor burnout.

Scoring & Ranking Algorithm

Eligible faculty are ranked using a multi-factor weighted equation:

Score = (W_spec × S_spec) + (W_load × S_load) + (W_perf × S_perf) + (W_tz × S_tz)
  • S_load (Load Balance): Preferentially weights instructors with lowest active student counts.
  • S_perf (Performance SLA): Incorporates historical student ratings and feedback compliance.
  • Tie-Breaking: Round-robin rotation among equal-scoring faculty members.

Resilient Fallback & Administrative Escalation Mechanism

If zero faculty members meet eligibility criteria during off-peak windows or sudden enrolment surges:

  1. Pending Allocation Queue: The request is safely written to mdl_local_acuitey_requests with status STATUS_PENDING.
  2. Automated Scheduled Retry Task: A background CLI task (\local_acuitey\task\retry_pending_routing) polls pending queues based on configured retry schedules.
  3. Administrative SLA Escalation: If a request remains unassigned beyond a configured threshold, the system generates an urgent notification to the Academic Administrator console for manual reassignment.
  4. Complete Auditability: Every evaluation cycle, calculated score, and exception is written to mdl_local_acuitey_routing_log.

Security in Acuitey LMS is governed by Moodle’s strict hierarchical Context Model, enforcing least-privilege role boundaries across student, faculty, and administrative tiers.

Acuitey Solutions LMS — Initial System Design Section 07: Payment & Enrolment Flow

7. Payment Architecture & Automated Enrolment

Acuitey supports dual Indian payment gateways—Razorpay and PhonePe—interfaced through Moodle’s native core_payment abstraction with mandatory server-side signature and payment-status validation.

Server-Side Secret Keys

Razorpay Key Secrets and PhonePe Salt/Merchant Keys reside strictly in encrypted database configurations on the Hostinger KVM. Client devices never receive private keys.

Gateway-Specific Verification

Enrolments occur exclusively when the server executes gateway-specific signature/authenticity checks, order amount verification, and payment status confirmation.

Idempotent Reconciliation

Transaction IDs are checked against mdl_payments prior to user enrolment, preventing duplicate course allocations or race conditions from webhook retries.

Acuitey Solutions LMS — Initial System Design Section 08: Zoom LTI Integration

8. Zoom LTI 1.3 Advantage Integration

Interactive live learning is integrated via LTI 1.3 Advantage (IMS Global Security Framework) using Moodle’s core mod_lti module and Zoom LTI Pro, eliminating passwords and unauthorized access.

Zero Password Exposure

Students and faculty never handle meeting passwords or direct Zoom account credentials. Access is cryptographically established using asymmetric RSA keypairs.

Zoombombing Prevention

Only authenticated users with active course enrolments can generate valid LTI tokens. External or unallocated participants cannot access live sessions.

Grade & Attendance Sync

Grade and attendance synchronization may be enabled where supported by the selected Zoom LTI configuration and Acuitey’s Zoom account/licensing using LTI AGS.

Acuitey Solutions LMS — Initial System Design Section 11: Implementation Sequence

11. Implementation Sequence & Execution Roadmap

The platform rollout follows a phased, 6-stage engineering sequence engineered to de-risk core dependencies, establish security baselines, and rigorously validate the dynamic routing engine prior to go-live.

STAGE 01

Infrastructure Provisioning & Hardening

Deploy Hostinger KVM (Recommended Ubuntu LTS), Nginx, PHP-FPM with OPcache, local Redis. Provision PostgreSQL / Supabase with connection pooling. Configure proposed Cloudflare edge security rules.

STAGE 02

Moodle Core Foundation & Payment Gateway Setup

Install untouched Moodle 5.2.3+ codebase. Configure MUC Redis caching and CLI cron task runner. Implement custom Razorpay and PhonePe gateway plugins with server-side gateway-specific verification.

STAGE 03

Acuitey Routing Engine Development (local_acuitey)

Create XMLDB table schemas (mdl_local_acuitey_*). Implement faculty matching algorithm, availability checking, and workload balancing services. Build background retry processor and pending queue.

STAGE 04

Zoom LTI 1.3 Advantage & Academic Workflows

Establish cryptographic OIDC/JWT handshake between Moodle mod_lti and Zoom LTI Pro. Configure course category taxonomies, assessment rubrics, gradebook aggregations, and Acuitey custom theme.

STAGE 05

Reporting, Administrative Consoles & Observability

Build Academic Administrator routing control dashboards and Finance payment reconciliation tools. Deploy proposed Prometheus/Grafana monitoring dashboards for real-time infrastructure telemetry.

STAGE 06

End-to-End Testing, Pilot Cohort & Production Go-Live

Conduct automated high-concurrency stress testing of routing algorithms. Execute end-to-end security audits. Train faculty and administrative staff. Execute production cutover and launch.
